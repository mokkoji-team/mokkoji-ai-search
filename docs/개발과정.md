# mokkoji-ai 개발 과정 및 최적화 요약

## 배경: 왜 만들었나

Spring Boot 백엔드에서 MySQL LIKE 쿼리(`utf8mb4_0900_ai_ci` collation)로 동아리/모집글의 모든 필드를 대상으로 검색하고 있었음. collation이 case-insensitive라 대소문자 매칭은 됐고, 모집글 내용까지 검색 대상이라 별칭("스마클")도 모집글에 해당 단어가 있으면 찾혔음. 하지만 다음 한계가 존재:

- **의도 기반 검색 불가**: "인공지능 배우고 싶어" 검색 시 해당 단어가 없는 AI 동아리는 결과에 안 나옴
- **유사 의미어 처리 불가**: "풋볼" → 축구 동아리, "그림" → 미술 동아리 등 매칭 안 됨
- **관련성 순위 없음**: 단순 매칭 여부만 판단, 얼마나 관련 있는지 점수화 불가
- **형태소 분석 없음**: "축구하는 동아리"와 "축구 동아리"가 다르게 취급될 수 있음

## 1단계: 데이터 준비 `8d13268`

동아리 데이터를 `data/clubs.json`으로 구조화. 각 동아리는 이름, 카테고리, 소속, 설명, 태그, 모집글 목록(`recruitments[]`)을 포함.

학습 데이터 `data/train_pairs.json`도 함께 준비 — `{"query": "AI 동아리", "club_id": 36}` 형식의 (쿼리, 동아리) 쌍.

## 2단계: 검색 엔진 핵심 구현 `63f9ede`

### `src/search.py` — ClubSearchEngine

**`club_to_text()`**: 동아리 정보를 하나의 문자열로 변환하는 핵심 함수. 이름 + 카테고리 한국어 변환 + 소속 + 설명 + 태그 + 모집글 제목/내용 전문을 이어붙임. `train.py`와 `serve.py` 양쪽에서 공유 — 이 함수가 다르면 학습 텍스트와 서빙 인덱스 텍스트가 달라지는 문제 방지.

**Hybrid Search**: 임베딩과 BM25를 합산.

```
hybrid_score = 0.7 × 임베딩점수 + 0.3 × BM25점수
```

- 고유명사(동아리 이름, 별칭) → BM25가 정확히 잡음
- "인공지능 배우고 싶어" 같은 의미 검색 → 임베딩이 담당
- 두 점수를 [0, 1]로 정규화 후 가중 합산
- 효과: "스마클" → SMARCLE 1위, "풋볼" → 축구 동아리 정상 검색

**임베딩 모델**: `BAAI/bge-m3` — 다국어 특화, 1024차원. 한국어-영어 혼용 검색에 강함.

## 3단계: 자연어 파싱 추가 `e7b7d6e`

### `src/query_parser.py`

"축구동아리 중에 모집글 많이 하는 곳" 같은 자연어 쿼리를 구조화된 인텐트로 분해.

```json
{
  "semantic_query": "축구",
  "sort_by": "recruitment_count",
  "sort_order": "desc",
  "category_filter": "SPORTS",
  "recruiting_now": null
}
```

**Ollama 로컬 LLM** (`qwen2.5:7b`) 사용 — 런타임 비용 $0. Claude API는 학습 데이터 생성 시에만 사용.

**LRU 캐시 512개**: `@lru_cache(maxsize=512)` — 동일 쿼리 반복 시 LLM 호출 없이 캐시에서 반환. Ollama 지연이 1~2초인 점을 고려한 최적화 (약 1초 단축).

## 5단계: FastAPI 서버 구현 `380738a`

### `src/serve.py`

Spring Boot에서 `POST /search` 또는 `POST /natural-search` 호출 후 `club_id` 목록 수신.

**2단계 검색 파이프라인 (`/natural-search`)**:

1. Ollama로 쿼리 파싱
2. `semantic_query`로 임베딩 검색 (후보 최대 30개)
3. `category_filter` / `recruiting_now` 필터
4. `threshold` 필터 (기본 0.3)
5. `bge-reranker-v2-m3` CrossEncoder로 정밀 재정렬
6. `sort_by`가 있고 Spring이 clubs 데이터 넘기면 AI 서버에서 직접 정렬, 아니면 `parsed_intent` 반환해 DB 레벨 정렬 위임

**`university_code` pre-filter**: 검색 후 필터링이 아니라 검색 전에 필터링.

- 문제: top_k=10 요청 시 전체에서 10개 뽑은 후 학교 필터 → 실제 결과 3~4개만 반환
- 수정: `search()`에 `filter_fn` 파라미터 추가, 유사도 계산 전 해당 학교 서브셋에만 검색
- 효과: top_k 항상 보장

**리랭커 후보 수 최적화**: top_k × 5~10 → `min(top_k × 2~3, 30)` 상한 적용. 리랭커 처리량 감소로 응답 속도 개선.

**응답에 club_name 추가**: `SearchResult`에 `club_name` 필드 추가. Spring Boot에서 club_id로 DB 재조회 없이 이름 바로 확인 가능.

**인덱스 CRUD 엔드포인트**:

- `POST /index/club` — 동아리 추가/업서트
- `PATCH /index/club/{id}/fields` — 기본 정보만 업데이트 (모집글 유지)
- `PATCH /index/club/{id}/recruitments` — 모집글만 업데이트 (기본 정보 유지)
- `DELETE /index/club/{id}` — 동아리 삭제
- `POST /index/rebuild` — 전체 재빌드

## 6단계: 파인튜닝 파이프라인 `4a3e4a6`

### `src/generate_pairs.py` — (쿼리, club_id) 학습 쌍 자동 생성

학습 데이터 전면 재생성:

- 문제: 기존 623쌍 중 73개 불일치, 78개 동아리 미커버
- 수정: 모든 필드 활용 (동아리 이름/설명/카테고리/소속/학교 + 모집글 제목/내용/상시모집)
- 효과: **671개 → 9,686개**, 211개 전 동아리 커버, 불일치 0개

생성 방식 3가지:

1. **자동 생성**: 동아리 이름, 설명 문장, 카테고리/소속/학교 조합, 모집글 제목/내용
2. **수동 curated 쌍**: 별칭("스마클" ↔ SMARCLE), 오타, 의도 기반 쿼리 직접 작성
3. **`--claude` 플래그**: Claude API(`claude-opus-4-8`)로 동아리당 쿼리 6개 추가 생성

### `src/train.py` — MultipleNegativesRankingLoss로 파인튜닝

- (anchor=쿼리, positive=club_to_text 결과) 쌍으로 학습
- 같은 배치 내 다른 쌍이 자동으로 negative sample
- 베이스 모델: `ko-sroberta-multitask` (빠른 테스트), `bge-m3` (야간, 3~5시간)
- 결과: `models/finetuned/` — serve.py의 `MODEL_PATH`를 이 경로로 변경하면 적용

파인튜닝 효과 (9,686개 학습쌍, 3 epochs, ko-sroberta-multitask):

| 쿼리 | 파인튜닝 전 | 파인튜닝 후 |
| --- | --- | --- |
| "스마클" | 0.737 | 0.769 |
| "머신러닝 프로젝트" | 0.807 | 0.863 |

**`src/demo.py`** — 파인튜닝 전후 검색 품질 비교 스크립트.

## 트러블슈팅

### MPS Out of Memory (bge-m3 파인튜닝)

- 오류: `RuntimeError: MPS backend out of memory (MPS allocated: 28~34 GiB, max: 36.27 GiB)`
- 원인: M-series Mac GPU 메모리 초과
- 해결: `TrainingArguments(use_cpu=True)` — 느리지만 안정적. 빠른 테스트 시엔 `ko-sroberta-multitask`로 대체

### datetime JSON 직렬화 오류

- 오류: `TypeError: Object of type datetime is not JSON serializable`
- 원인: DB에서 불러온 `created_at`, `updated_at`이 Python datetime 객체 그대로 저장됨
- 해결: `db_loader.py`에서 `str(row["created_at"])` 변환

### `recruiting_now` 필터 미작동

- 원인: `serve.py`의 `_is_recruiting()`이 `start_date`/`end_date` 키를 참조했으나, `db_loader.py`는 `recruit_start`/`recruit_end`로 저장
- 해결: `r.get("recruit_start") or r.get("start_date")` 폴백 방식으로 수정

### 인덱스 파일 손상

- 원인: 서버 강제 종료 시 `clubs.json` 쓰기 중단으로 파일 손상
- 해결: `rm -rf index/` 후 서버 재시작 → DB에서 자동 재빌드
